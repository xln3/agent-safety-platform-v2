## 四、需跟进缺陷（4 项）

### 缺陷 #1（已知 / V2 报告已记） — `EvalJob.totalSamples=0` 在样本由 inspect_ai 动态枚举时未回填

**表征**：A5 截图中 job 41 显示「367 / 0 项」，0 是 totalSamples 字段未初始化的结果。
**影响**：进度页分母错乱，但不影响功能。
**位置**：`server/eval-engine/ts_bridge_solver.py` 第一次回调时未同步回填 totalSamples。
**优先级**：P2（仅 UI 展示问题）。

### 缺陷 #2（新发现） — 僵尸 job 没有死锁检测

**表征**：job 41 启动于 2026-04-28T02:17，最后 DB 写入 03:04:40，截至 11:04（审计时刻）已 8 小时无任何状态变化，但 status 仍 = "running"，UI 进度页可访问且显示 56% 进度（A12 截图），用户无法判定它是否还活着。
**影响**：
- 用户层面：无法手动终止此类 job（UI 「取消评估」按钮存在但实测点击无效，需验证）。
- 运行时：可能阻塞后续 job 的并发槽位。
**建议**：
1. backend 加一个 watchdog，对 `updatedAt` 距今 > N 分钟（如 30m）的 running job 自动置 stale；
2. 进程退出 / 子进程死亡时确保把所属 job 标记 failed（当前疑似缺这条 cleanup 路径）；
3. UI 进度页对 stale job 显示「最近一次心跳：xxx 前」并启用强制终止。
**位置**：`server/src/services/evalRunner.ts`（job lifecycle 管理）。
**优先级**：P1（直接影响生产可用性）。

### 缺陷 #3（新发现） — 多个本地 benchmark scorer 缺 `JUDGE_MODEL_NAME` 环境变量时静默失败

**表征**：job 40 status=failed，task agentharm/safeagentbench 报错：
```
[safeagentbench/scorer] JUDGE_MODEL_NAME not set in .env, falling back to 'GLM-4.7'
[open_agent_safety/scorer] JUDGE_MODEL_NAME not set, falling back to 'gpt-4o'
```
回退模型实际不可达 → 子任务 0 样本评分。
**影响**：
- 没配 `JUDGE_MODEL_NAME` 的环境，凡是用本地实现 scorer 的 benchmark（agentharm / safeagentbench / open_agent_safety / 其他）都会评分失败；
- 与 V2 重构后引入的 JudgeModel 实体不联动 —— 即使 UI 创建了裁判模型，本地 scorer 仍读 `JUDGE_MODEL_NAME` 环境变量而不是 job.judgeModel。
**建议**：
1. 短期：DELIVERY.md / DEPLOY.md 显式要求设置 `server/.env` 的 `JUDGE_MODEL_NAME`，或在 `npm run db:sync` 后做一次配置自检；
2. 中期：把本地 scorer 的 `JUDGE_MODEL_NAME` 读取替换为从 job.judgeModel 配置注入（与 inspect_ai 原生 grader 走同一注入路径）。
**位置**：`server/eval-engine/benchmarks/eval_benchmarks/{safeagentbench,open_agent_safety,agentharm}/scorer.py`。
**优先级**：P1（直接影响 4 大分类中 tool_calling、task_planning 类基准的可用性）。

### 缺陷 #4（新发现） — 部分子任务失败时综合评估"过度乐观"

**表征**：A11a 截图中 job 40 综合评估显示「稳健 100 / 100 ⭐⭐⭐⭐⭐」，但小字显示「1 / 3 个任务已产出结论」，agentharm（0/2）/ agentharm_benign（0/2）实际未出分被默默剔除出平均。
**影响**：业务方一眼看到「100 分稳健」会误判 agent 无问题；真相是只跑出来 1/3 评分点。
**建议**：
1. 综合评估卡片仅在 `产出任务/总任务 ≥ 80%` 才给五星和「稳健」标签，否则降级为「数据不足」并提示失败任务清单；
2. 维度评估 banner 在子任务失败时显式标红「N / M 失败」，不要把失败任务藏在折叠区。
**位置**：前端结果页 `src/page/EvalResultsPage.tsx`（综合评估卡片渲染逻辑）+ 后端 `byCategory` 聚合（建议把 unsuccessful_count 一并返回）。
**优先级**：P0（误导客户验收的高风险 UX 缺陷）。

### 已知限制 #5（V2 报告已记） — `EvalItem.score` / `scoreLabel` sample-level 评分尚未回填

inspect_ai grader 阶段产出的样本级 score 当前未持久化到 EvalItem.score 字段（仍为 null，A7c 截图可见），仅 task-level rawScore/safetyScore 正确。不影响 KPI / 雷达图，但影响"高危案例"和"样本明细"的红黄绿标签。

## 八、修复记录 2026-04-28（同日落地，4 项缺陷全部修复）

> 修复人：Claude（Opus 4.7） / 修复日期：2026-04-28（与审计同日） / 验证方式：Playwright 全量复跑 + 后端 HTTP 双重校验 + DB 真值核对

### M1 ── 修复缺陷 #4（P0：综合评估"过度乐观"）

**根因**：后端聚合只算"已出分任务的均值"，没有把"未出分任务数"作为门禁条件传给前端；前端 `FullReportView` / `AssessmentSummary` 无差别按数值映射星级。

**改动**：
- `server/src/controllers/resultController.ts`：聚合返回新增 `failedTaskCount` / `coverage`（在 [0,1] 区间）/ `aggregateStatus`（`sufficient`≥80% / `insufficient`<80% / `no_data`=0）。
- `src/services/evalService.ts`：`JobResultData.aggregate` 与 `BenchmarkInfo.judgeModel` 类型扩展。
- `src/components/eval/AssessmentSummary.tsx`：新增 `tierOverride` 入参，`insufficient` / `no_data` 直接显示「数据不足」/「暂无数据」并隐藏分值。
- `src/components/eval/FullReportView.tsx`：`aggregateStatus !== 'sufficient'` 时禁用星级，红色 caption 显示「N 个任务未出分（请检查裁判模型 / JUDGE_MODEL_NAME 配置）」与「⚠ 数据覆盖率 X% — 暂不评定星级」。

**证据**：`_worklog/04-screenshots/audit-2026-04-28/A11a-results-job40-overview.png`（修复后截图）— job 40 显示「数据不足」、红字「2 个任务未出分」、「⚠ 数据覆盖率 33% — 暂不评定星级」，原先误导性的「稳健 100/100 ⭐⭐⭐⭐⭐」已消失。

### M2 ── 修复缺陷 #3（P1：缺裁判时静默失败）

**根因**：用户可在不选 judgeModel 的情况下提交 `agentharm` / `safeagentbench` 等需裁判的 job，运行时 scorer 回退到不可达默认（gpt-4o / GLM-4.7）→ 0 样本评分。

**改动**：
- `server/eval-engine/benchmarks/catalog.yaml`：给 `agentharm` 显式声明 `judge_model: alicloud-qwen3.5-plus`，并把 `refusal_judge` / `semantic_judge` 写进 `task_args`（agentharm 用 task_args 注入裁判，不读 env）。
- `server/src/controllers/evalController.ts`：`POST /api/eval/jobs` 严格门禁 — 选了 catalog 中带 `judge_model` 字段的 benchmark 但未传 judgeModel/judgeModelId 时直接 400 + 中文错误列出受影响 benchmark。
- `src/page/EvalNewPage.tsx`：替换原裁判自由文本框为 `judgeModelService.list()` 拉取的 Select；按所选 benchmark 的 `judgeModel` 字段动态计算 `judgeRequired`，必填时显示红星 + 错误态 help text + 提交按钮 disable；改用 `judgeModelId`（数字 ID）发送，弃用 legacy 字符串。

**证据**：
- 命令行核验 ── `curl POST /api/eval/jobs {agentharm without judge}` → `{"code":-1,"message":"以下 benchmark 需要裁判模型但未选择 judgeModel/judgeModelId: agentharm"}`（HTTP 400）。
- xstest（catalog 无 judge_model）无裁判提交仍 200 OK，门禁仅命中需裁判的 benchmark。

### M3 ── 修复缺陷 #2（P1：僵尸 job 无 watchdog）

**根因**：`recoverJobs()` 只在服务启动时跑一次；server 不重启的话，子进程死了、ts-bridge 回调断了的 job 永远卡 `running`。

**改动**：
- 新增 `server/src/services/jobWatchdog.ts`：`setInterval` 每 5min 扫一次，`updatedAt` 距今 > 30min 且关联 task 也无新写入的 `running` job 自动置 `failed`，per-task `errorMessage='[STALE] 长时间无进度（X 分钟未更新），自动判定失败'`，并通过 SSE `job.finish` 事件广播 `reason: 'stale'`。
- `server/src/index.ts`：在 `recoverJobs()` 之后调 `startWatchdog()`，启动 30s 后先跑一次（兜底重启时机偏差），之后按 5min 周期。
- 注意：`EvalJob` 模型无 `errorMessage` 列（与 evalRunner 现状一致），错误信息只持久到 task 行 + SSE 载荷，job 行只置 status=failed + completedAt。

**证据**：服务启动日志 — `[INFO] Job watchdog started (check every 5min, stale=30min)`。

### M4 ── 修复缺陷 #1（P2：进度页"X / 0 项"）

**根因**：`EvalJob` 表里 `totalSamples` 与 `totalItems` 是两个名字不同但语义相同的字段，后端只在 `bumpTotalsToAtLeastCompleted` 里 bump `totalSamples`，前端 `EvalListPage` 第 134 行恰恰读 `totalItems` —— 两个字段各走各的，造成「X 已完 / 0 项总数」。

**改动**：
- `server/src/controllers/evalController.ts`：job 创建时 `totalSamples` 与 `totalItems` 同步初始化为 `limit × task_count`（无 limit 时为 0）。
- `server/src/controllers/internalAgentRunnerController.ts` 中 `bumpTotalsToAtLeastCompleted`：把 `totalItems = GREATEST(total_items, completed_items)` 一并写回，与现有 `totalSamples` 逻辑对齐。
- DB 一次性回填：`UPDATE eval_jobs SET total_items = GREATEST(total_items, total_samples, completed_items) WHERE total_items < GREATEST(total_samples, completed_items)` —— 历史 39 条 job 全部修齐。

**证据**：
- `_worklog/04-screenshots/audit-2026-04-28/A5-eval-list.png`：job 41 显示「539 / 539 项」（原审计为「539 / 0 项」），job 39「20 / 20 项」、job 40「2 / 6 项」全部正常。
- 新建测试 job（limit=1, xstest）后 `GET /api/eval/jobs/{id}`：`totalItems=1, totalSamples=1` 同步初始化（之前为 0）。
